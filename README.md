# Практична робота № 2

## Тема: Сокетне програмування та обмін повідомленнями по TCP/UDP

---

## Мета роботи

- Опанувати принципи низькорівневого сокетного програмування за допомогою стандартного пакета `net` мови Go.  
- Засвоїти архітектурну модель сервера «горутина на кожне з'єднання» для паралельного обслуговування мережевих клієнтів.  
- Спроєктувати та реалізувати текстовий протокол прикладного рівня з розділювачем для передачі команд і повідомлень.  
- Реалізувати потокобезпечну реєстрацію підключених клієнтів та механізм широкомовної розсилки повідомлень (Broadcast).  
- Опанувати прийом датаграм через протокол UDP та організувати плавне завершення роботи сервера (Graceful Shutdown).

## Короткі теоретичні відомості

### 1\. Сокети Берклі та TCP-сервер у Go

Мережевий сокет — це програмна кінцева точка з'єднання, через яку процес обмінюється даними з мережею (в операційних системах Unix сокет розглядається як різновид файлового дескриптора).

Для створення TCP-сервера стандартна бібліотека Go надає функцію `net.Listen`, яка створює слухача `net.Listener`. Обслуговування нових підключень виконується через блокуючий виклик методу `Accept()`, після чого для кожного клієнта запускається окрема легковажна горутина:

listener, err := net.Listen("tcp", ":9000")

if err \!= nil {

    log.Fatal(err)

}

defer listener.Close()

for {

    conn, err := listener.Accept()

    if err \!= nil {

        break

    }

    go handleConnection(conn) // Окрема горутина на клієнта

}

---

### 2\. Потокове введення/виведення та протокол з розділювачем

Протокол TCP передає безперервний потік байтів без збереження меж повідомлень. Тому прикладному протоколу потрібен механізм розділення окремих команд. Найпростіший спосіб — використання символу нового рядка (`\n`) як термінатора повідомлення.

Для зручного читання рядків використовується буферизований читач пакета `bufio`:

reader := bufio.NewReader(conn)

for {

    message, err := reader.ReadString('\\n')

    if err \!= nil {

        break // Клієнт розірвав з'єднання

    }

    // Обробка отриманого рядка

}

---

### 3\. Прийом датаграм через протокол UDP

На відміну від TCP, протокол UDP не встановлює постійного з'єднання і передає дані окремими ізольованими пакетами — датаграмами. Для прослуховування UDP-порту використовується функція `net.ListenPacket`, яка повертає інтерфейс `net.PacketConn`:

packetConn, err := net.ListenPacket("udp", ":9001")

if err \!= nil {

    log.Fatal(err)

}

defer packetConn.Close()

buffer := make(\[\]byte, 1024\)

n, clientAddr, err := packetConn.ReadFrom(buffer)

if err \== nil {

    data := string(buffer\[:n\])

    \_ \= data

    \_ \= clientAddr

}

---

### 4\. Плавне завершення (Graceful Shutdown)

Для безпечної зупинки сервера без раптового обриву клієнтів застосовується перехоплення сигналів операційної системи (`SIGINT`, `SIGTERM`) за допомогою пакета `os/signal`:

stopChan := make(chan os.Signal, 1\)

signal.Notify(stopChan, os.Interrupt, syscall.SIGTERM)

\<-stopChan // Блокування до натискання Ctrl+C або команди зупинки процесу

## Постановка задачі

У розподілених системах керування та диспетчеризації (наприклад, IoT-платформах або серверах моніторингу) часто поєднуються два типи взаємодії:

1. **Швидкий прийом показників телеметрії по UDP:** датчики надсилають стан без гарантій доставки з мінімальною затримкою;  
2. **Надійне з'єднання по TCP:** диспетчери або клієнтські застосунки підключаються для отримання оперативних сповіщень у реальному часі та надсилання команд керування.

Необхідно розробити консольний **мережевий сервіс диспетчеризації та телеметрії (Device & Dispatcher Gateway)**, який одночасно обслуговує TCP-клієнтів, приймає UDP-датаграми та безпечно транслює інформаційні події між усіма учасниками мережі.

Клієнтами для взаємодії з цим сервером можуть виступати:

- термінальні утиліти командного рядка (`nc`, `telnet`, Ncat);  
- власний тестовий клієнт на Go;  
- будь-які зовнішні застосунки (десктопні програми на C\# WPF/Avalonia, JavaFX, мобільні додатки чи вебклієнти).

## Завдання

Практична робота складається з трьох послідовних рівнів. Кожен наступний рівень базується на попередньому та розширює функціональність розроблюваного рішення.

### Рівень 1\. Базовий: Багатопотоковий TCP-сервер команд

1. **Ініціалізація проєкту:**  
   - Створити окрему робочу директорію для практичної роботи.  
   - Ініціалізувати Go-модуль за допомогою команди `go mod init <назва_модуля>`.  
   - Створити файл `main.go`.  
2. **Створення TCP-слухача:**  
   - Відкрити TCP-сокет на визначеному порті (наприклад, `:9000`) за допомогою функції `net.Listen`.  
   - Організувати головний цикл прийняття вхідних з'єднань за допомогою методу `Accept()`.  
   - Для кожного нового підключення викликати функцію-обробник в окремій горутині через ключове слово `go`.  
3. **Реалізація текстового протоколу команд:**  
   - Забезпечити построкове читання даних від клієнта за допомогою `bufio.NewReader` та методу `ReadString('\n')`.  
   - Очищати отриманий рядок від символів переносу рядка (`\r`, `\n`) за допомогою `strings.TrimSpace`.  
   - Реалізувати обробку базових команд:  
     - `ECHO <повідомлення>` — повертає вхідний текст назад клієнту з префіксом `[ECHO]: ...`;  
     - `TIME` — повертає клієнту поточний час сервера у форматі `time.RFC3339`;  
     - `CLOSE` або `QUIT` — надсилає прощальне повідомлення та розриває поточне мережеве з'єднання (`conn.Close()`);  
     - у разі невідомої команди надсилати клієнту повідомлення про помилку з підказкою списку доступних команд.  
4. **Тестування роботи:**  
   - Підключитися до сервера за допомогою мережевого клієнта (`nc localhost 9000` або `telnet localhost 9000`).  
   - Перевірити коректність виконання всіх команд та одночасне підключення щонайменше двох незалежних клієнтів.

---

### Рівень 2\. Конкурентний: Потокобезпечна реєстрація та широкомовна розсилка (Broadcast)

1. **Збереження функціональності Рівня 1\.**  
2. **Менеджер активних клієнтів:**  
   - Оголосити структуру сервера, яка зберігає список або асоціативний масив (`map`) активних підключень.  
   - Забезпечити захист колекції підключень від стану гонитви за допомогою примітива синхронізації `sync.Mutex` або `sync.RWMutex`.  
   - При успішному підключенні клієнта додавати його дескриптор до загального списку та виводити системне сповіщення про нове з'єднання.  
   - При розриві з'єднання гарантовано видаляти клієнта з колекції (через конструкцію `defer`).  
3. **Реалізація широкомовної розсилки:**  
   - Додати нову команду протоколу:  
     - `BROADCAST <повідомлення>` або `MSG <повідомлення>` — надсилає отриманий текст **усім іншим активним клієнтам**, підключеним до сервера.  
   - Під час розсилки проходити по списку підключень під захистом блокування і записувати дані в кожне з'єднання через метод `Write`.  
   - Також надсилати системні сповіщення всім учасникам про приєднання нового клієнта та його вихід із мережі.  
4. **Діагностика потокобезпечності:**  
   - Відкрити 3 окремі термінали, підключитися до сервера та перевірити обмін повідомленнями між ними.  
   - Запустити сервер із прапорцем виявлення стану гонитви пам'яті:  
       
     go run \-race .  
       
     Переконатися у відсутності попереджень DATA RACE під час масової розсилки повідомлень.

---

### Рівень 3\. Просунутий: Прийом UDP-телеметрії та Graceful Shutdown

1. **Збереження функціональності попередніх рівнів.**  
2. **Паралельний UDP-сервер прийому метрик:**  
   - В окремій горутині відкрити UDP-сокет на сусідньому порті (наприклад, `:9001`) через `net.ListenPacket("udp", ":9001")`.  
   - У безперервному циклі вичитувати датаграми у буфер фіксованого розміру за допомогою методу `ReadFrom`.  
   - Отримані дані телеметрії (наприклад, покази віртуальних сенсорів або повідомлення статусу) автоматично форматувати та транслювати усім підключеним TCP-клієнтам із позначкою `[TELEMETRY from <адреса_сенсора>]: <дані>`.  
   - Протестувати надсилання UDP-датаграм за допомогою команди:  
       
     nc \-u localhost 9001  
       
     та переконатися, що всі TCP-клієнти миттєво отримують сповіщення про отримані метрики.

     
3. **Реалізація плавного завершення роботи сервера (Graceful Shutdown):**  
   - Налаштувати перехоплення сигналів завершення процесу `os.Interrupt` (`SIGINT`) та `syscall.SIGTERM` через канал `chan os.Signal`.  
   - При надходженні сигналу (наприклад, натискання Ctrl+C у консолі сервера):  
     - надіслати всім активним TCP-клієнтам фінальне сповіщення `SERVER_SHUTTING_DOWN`;  
     - коректно закрити всі клієнтські мережеві з'єднання;  
     - закрити слухачі TCP та UDP;  
     - дочекатися завершення обслуговуючих горутин та безпечно зупинити процес.

## Контрольні питання

1. Чим відрізняється робота з потоковим сокетом TCP від роботи з датаграмним сокетом UDP на рівні системних викликів і пакета `net`?  
2. Чому протокол TCP не зберігає межі повідомлень і як це питання вирішується на прикладному рівні за допомогою розділювачів або довжини?  
3. Чому архітектура «горутина на кожне з'єднання» є природною та масштабованою у Go порівняно з потоками операційної системи?  
4. Навіщо при роботі зі списком підключених клієнтів застосовувати `sync.Mutex` або `sync.RWMutex`? До чого призведе одночасне читання та запис без блокування?  
5. У яких прикладних сценаріях використання протоколу UDP є більш доцільним, ніж TCP, незважаючи на відсутність гарантій доставки?  
6. Як працює механізм перехоплення сигналів ОС у Go та чому важливо реалізовувати Graceful Shutdown для мережевих серверів?  
7. Чи зможуть десктопні або мобільні клієнти (написані іншими мовами) працювати з цим Go-сервером, якщо вони дотримуються описаного протоколу команд?
